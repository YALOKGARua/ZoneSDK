# Версії ZoneSDK

Тут сказано, що обіцяє номер версії ZoneSDK, що належить до публічного API і як перенести аддон на новіший випуск.

Англійська версія: [VERSIONING.md](VERSIONING.md). Див. також [API-UA.md](API-UA.md), [RULES-UA.md](RULES-UA.md), [PATCH_DAY-UA.md](PATCH_DAY-UA.md) і [CHANGES-UA.md](../CHANGES-UA.md).

## 1. Номери версій

ZoneSDK використовує семантичне версіонування, `major.minor.patch`, для свого **API вихідного коду**.

Двійкового інтерфейсу між аддонами і ZoneSDK немає. Кожен аддон компілює власну копію вихідного коду ZoneSDK з того випуску, який закріплює його `build\zsdk.lock`, і ця копія живе всередині його `.addon64`. Тому:

- аддони, зібрані на різних версіях ZoneSDK, працюють поруч в одній грі;
- новий випуск ZoneSDK нічого не змінює в уже зібраному аддоні: зміни з'являються, коли автор перезбирає і заново випускає аддон;
- аддони не мають спільного стану через ZoneSDK. Кожен має власний тег, власне повідомлення для потоку гри, власний м'ютекс одного екземпляра і власну теку даних.

| випуск | що може містити |
|---|---|
| **patch** (з 1.0.0 на 1.0.1) | виправлення помилок і нові рядки версій гри, щоб SDK знав новий exe гри: `guard::Build` у `guard::kBuilds`, її тека `data\builds\<id>` і власні набори захисту SDK для неї. Жодних нових можливостей |
| **minor** (з 1.0 на 1.1) | доповнення: нові заголовки, функції, типи і константи; поля, додані в кінець структури; значення переліку, додані перед `Count`; нові правила тестів, спершу як попередження |
| **major** (з 1.x на 2.0) | зміни, що ламають сумісність, з попередженням заздалегідь |

Оновлення гри 2.1 (збірка `2bd3f115`, вийшла в Steam 26 жовтня 2026 року) вийшло ще до випуску 1.0.0, тож 1.0.0 уже знає його поряд із `61bc1e03`. Коли наступне оновлення гри можна підтримати, його збірка приходить саме таким patch-випуском ([PATCH_DAY-UA.md](PATCH_DAY-UA.md)).

## 2. Що публічне

Обіцянка стосується:

- заголовків у `include/zsdk`, крім внутрішніх назв, перелічених нижче;
- параметрів `Invoke-ZsdkBuild` у `build\zsdk.psm1`, яку викликає `build\make.ps1` кожного аддона: `-Root`, `-Lock`, `-Name`, `-Define`, `-Config`, `-Tests`, `-Deterministic`, `-Pure`, `-Legacy`, `-Libs`, `-Includes`, `-Defines`, `-CompilerFlags`, `-LinkFlags`, `-WaitMinutes`, `-Exe`, `-LiveExe`, `-RequireExe`, `-Verify`;
- форматів `build\zsdk.lock` (`version=`, `manifest=`, `home=`) і `tests\zsdk.cfg` (ключі з [розділу 10 RULES-UA.md](RULES-UA.md#zsdkcfg));
- теки даних: у `%LOCALAPPDATA%\<Identity::folder>` лежать ini, журнал, попередній журнал, мітка виходу `<назва ini>.exit` і `report.txt`. Секції ini `[safety]` і `[proven]` належать SDK; секції і ключі, яких він не знає, переживають кожен перезапис;
- назв, які один аддон може побачити в іншого: тег, повідомлення для потоку гри `<tag>.GameThread.1` і м'ютекс `Local\<tag>.Addon.<pid>`.

Не публічні: усе в `src`, кожен простір імен `detail`, внутрішні назви нижче, тексти журналу і точний вигляд діагностики. Заголовки тестів у `include/zsdk/test`, якими користуються тести аддонів (`check.h`, `scan.h`, `addon.h`), публічні.

### Структури і переліки

- Структура публічного API отримує нові поля лише **в кінці**. У межах однієї major-версії поля ніколи не прибирають, не переставляють і не змінюють їхнього типу.
- Перелік отримує нові значення лише **перед `Count`** (або в кінці, якщо `Count` немає). Значення ніколи не прибирають і не перенумеровують.
- Тому заповнюйте кожну структуру позначеними ініціалізаторами (designated initializers), а решту хай покривають типові значення:

```cpp
.row = zsdk::registry::Row{ .id = "myhud", .tag = "AuthorMyHud", .lane = 0.66f, .keys = "ALT+H" },
```

- `guard::Set` потребує назви-літерала, позначеної, `guard::Set kCoreSet{ .name = "myhud.core", ... }`, або першим значенням у фігурних дужках, бо набір тестів `zsdk-guards` знаходить оголошені набори саме за цим рядком ([RULES-UA.md, розділ 6](RULES-UA.md#appsets-запишіть-кожен-набір-захисту)).

### Теги стабільності

Кожна публічна назва має один тег стабільності:

| тег | обіцянка |
|---|---|
| **Stable** | усе, що не позначено інакше; діють правила вище |
| **Provisional** | може змінитися чи зникнути в minor-випуску, завжди з приміткою в CHANGES. У 1.0: `zsdk::registry`, `zsdk::job`, `zsdk::census` і перевірки екрана з `zsdk/verbs/common.h` (`common::kScreen` і його значення `Screen`) |
| **Legacy** | залишено для аддонів, написаних до ZoneSDK; може зникнути у 2.0. У 1.0: перемикачі `Policy` `marks`, `knock` (разом з `knockMs` і `idleMs`), `wire` (разом з `wireMs`), `gone`, `spelling`, `widen` і `census` та їхні переліки. Новий аддон лишає типові значення |
| **Internal** | не для аддонів, без обіцянок: кожен простір імен `detail`, `zsdk/test/ledger_raw.h`, `zsdk/test/hardrules.h`, `ini::*Raw`, `ledger::Calm`, `log::Hushed`, `log::Due`, `thread::Booked`, `thread::Rejected` |

Теги записано в `release\<версія>\tools\api\tags.txt`. Кожен випуск має також `release\<версія>\api\<версія>.txt`: перелік його публічних оголошень, по одному в рядку, з тегом в останньому стовпці. Внутрішніх назв у ньому немає.

## 3. Як дотримуються обіцянки

Інструмент випуску створює перелік API нового випуску і порівнює його з попереднім випуском тієї самої major-версії. Він відмовляє у випуску, якщо minor- чи patch-випуск прибирає публічну назву, змінює сигнатуру чи тип, прибирає, переставляє чи змінює поле структури або прибирає, переставляє чи перенумеровує значення переліку. Зміна будь-чого з тегом Provisional проходить у minor-випуску з приміткою, а в patch-випуску відхиляється.

Те саме порівняння двох випусків можна запустити самому, з теки ZoneSDK:

```
powershell -NoProfile -ExecutionPolicy Bypass -File release\1.1.0\tools\api\surface.ps1 -Compare release\1.0.0\api\1.0.0.txt -With release\1.1.0\api\1.1.0.txt -Kind minor
```

Він виводить кожну додану назву, кожну примітку і кожну відхилену зміну, потім `api compare (minor): N added, N notes, N refused`; якщо якусь зміну відхилено, він завершується помилкою.

Ще дві обіцянки:

- **Нові правила тестів починаються з попереджень.** Нове правило загальних наборів тестів приходить у minor-випуску як попередження, тож аддон, який збирався раніше, збирається й далі.
- **Про вилучення попереджають на один minor-випуск наперед.** CHANGES називає назву з тегом Provisional до того, як вона зміниться чи зникне, а назву, яку прибере 2.0, — ще до 2.0.

## 4. Випуски ніколи не змінюються

- Теку випуску `release\<версія>` після створення ніколи не редагують. `MANIFEST.sha256` містить SHA-256 кожного файлу, і кожне збирання звіряє з ним теку та зупиняється, якщо файл змінено, додано чи вилучено (у розпакованому пакеті файли не позначені як лише для читання). Виправлення виходить новим випуском.
- `build\zsdk.lock` закріплює один випуск за його версією і за SHA-256 його `MANIFEST.sha256`. Збирання шукає теку випуску, чий маніфест має саме цей хеш, і відкидає кожну іншу копію з тим самим номером версії.
- Набір тестів `zsdk-hardrules` перевіряє це закріплення під час кожного запуску тестів.

### Перенесення аддона на новіший випуск

1. Розпакуйте новий пакет ZoneSDK. Його випуск лежить у `ZoneSDK-<версія>\release\<версія>`.
2. Прочитайте [CHANGES-UA.md](../CHANGES-UA.md) для версій між старою і новою.
3. Отримайте хеш нового маніфесту, з нової теки ZoneSDK:

   ```
   powershell -NoProfile -Command "(Get-FileHash 'release\1.0.1\MANIFEST.sha256').Hash"
   ```

4. У `build\zsdk.lock` свого аддона поставте `version=` на нову версію, а `manifest=` — на цей хеш. Якщо в закріпленні є рядок `home=`, вкажіть у ньому нову теку ZoneSDK відносно теки аддона; без `home=` задайте змінну `ZSDK_ROOT` з цією текою або тримайте аддон усередині неї.
5. Перевірте, де збирання тепер знаходить ZoneSDK: `.\build.cmd -Where` виводить теку випуску і те, як її знайдено, нічого не збираючи.
6. Запустіть `.\build.cmd -Tests -Verify`, перевірте в грі і випустіть аддон з його власною новою версією.

У межах однієї major-версії цього досить, якщо ви не користуєтеся назвою з тегом Provisional, яка змінилася; CHANGES про це скаже. Власні тести SDK і порівняння API вище не дають minor- чи patch-випуску зламати аддон, який збирається на попередньому випуску.
