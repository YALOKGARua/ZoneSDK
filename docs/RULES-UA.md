# Правила ZoneSDK

Тут зібрано правила для аддонів ReShade на ZoneSDK 1.0. Більшість із них не поради: їх перевіряють компілятор, сам SDK під час роботи або набори тестів, які запускаються під час кожного `build.cmd -Tests`. Для кожного правила сказано, у чому воно полягає, навіщо воно потрібне і яка перевірка його ловить.

Коли загальний тест не проходить, збирання виводить помилку, а під нею назву набору, наприклад:

```
FAIL no std::thread in src/scan.cpp: background work runs through zsdk::job::Every on the SDK worker, never on an own thread, timer or pool callback
zsdk-hardrules: 303 checks, 1 failures
zsdk-hardrules: docs\RULES.md (docs\RULES-UA.md in Ukrainian), section 10, zsdk-hardrules, gives the rule behind each message of this suite
FAIL zsdk-hardrules (1)
```

Знайдіть назву набору (`zsdk-hardrules`) у [розділі 10](#10-загальні-набори-тестів), як і підказує рядок під підсумком: там перелічено всі повідомлення цього набору і правила, що за ними стоять. Повідомлення тестів і журналу пишуться англійською, тож нижче вони наведені так, як їх виводить збирання.

Англійська версія: [RULES.md](RULES.md). Див. також [GETTING_STARTED-UA.md](GETTING_STARTED-UA.md), [API-UA.md](API-UA.md), [VERSIONING-UA.md](VERSIONING-UA.md) і [PATCH_DAY-UA.md](PATCH_DAY-UA.md).

## 1. Слова, що вживаються тут

- **Модуль кадру** (present unit): вихідний файл у `src`, поза `src\overlay`, окрім `src\entry.cpp`. Він компілюється без ImGui.
- **Модуль оверлею** (overlay unit): файл у `src\overlay`. У ньому можна використовувати ImGui і помічники `zsdk::tab` та `zsdk::paint`.
- **Помпа** (pump): такт SDK у потоці гри. SDK під'єднується до циклу повідомлень гри і виконує один такт, коли надходить його повідомлення пробудження.
- **Виклик гри**: виклик функції гри через `zsdk::Call` і `zsdk::Fire`.
- **Ключ**: назва виклику гри або блоку вашого коду в реєстрі збоїв, наприклад `Actor.K2_GetActorLocation` чи `myhud.camera`.
- **Смуга** (lane): висота на екрані, де малюються ваші спливні підказки (toasts), як частка висоти екрана. Не плутайте її з лініями огорожі збоїв SDK: їх 16, по одній на кожну частину роботи в подіях ReShade (хуки аддона і власна робота SDK), кожна з ключем реєстру `present.<lane>` ([розділ 5.5](#55-коли-щось-падає)).

## 2. Потоки: що де може виконуватися

Аддон працює в шести видах потоків. Кожен хук виконується в одному з них.

| потік | хуки, що там виконуються | можна | не можна |
|---|---|---|---|
| **кадр** (present): потік рендерингу, подія ReShade `reshade_present` | `boot` (один раз, на першому кадрі), `frame(Input)`, `opened(bool)` | читати `Input`; читати налаштування (`ini::Config`); просити потік гри про роботу через `thread::Ask(order)`; додавати підказки; писати в журнал; читати копії (`world::Snapshot()`, власний знімок під власним блокуванням); реєструвати завдання через `job::Every` (лише в `boot`) | ImGui, `zsdk::tab`, `zsdk::paint` (модуль кадру з ними не скомпілюється); створювати `Call` чи викликати `Fire` (відмова); писати в пам'ять гри (відмова); `world::Hold()` (ви отримаєте копію і рядок у журналі); чекати чи блокуватися, бо це затримує кадр |
| **оверлей**: потік рендерингу всередині кадру ImGui від ReShade (`reshade_overlay` і вкладка аддона) | `overlay(Overlay&)`, `page(Overlay&)`, `words`, `tone`; `report`, коли гравець натискає «Скопіювати звіт» (він лише повертає текст) | ImGui, `zsdk::tab`, `zsdk::paint` (у модулях оверлею); читати свій знімок під своїм блокуванням; змінювати налаштування через `ini::Apply`; підказки | створювати `Call` чи викликати `Fire`; писати в пам'ять гри; `world::Hold()`; повільну роботу, бо це виконується щокадру |
| **D3D**: події ReShade `init_pipeline`, `bind_pipeline`, `destroy_pipeline` і `destroy_device` у будь-якому потоці рендерингу, RHI чи компіляції шейдерів, часто в кількох одночасно, і ще до `boot` | `pipelineInit`, `pipelineBind`, `pipelineDestroy`, `deviceDestroy` | пристрій і список команд ReShade; читання без блокувань; короткі власні блокування | `Fire`, `world::Hold()`, ImGui, вікна збою, записи в ini; будь-що повільне в `pipelineBind`, який виконується для кожного прив'язаного конвеєра: тримайте його складність на рівні O(1) |
| **потік гри**: помпа | `refresh`, `prime`, `advance`, `step(now)`, `hot`, `publish(now)`, `turn`, `order`, `orderName`; іноді `quit` | виклики гри; записи в пам'ять гри всередині вікна збою (`mem::Write`); `world::Hold()`; підказки; налаштування | ImGui (код помпи — це код модулів кадру); спати чи чекати на інший потік; довгу роботу: такт понад 5 мс журнал позначає як `slow tick` |
| **робочий потік SDK**: один потік на аддон, з назвою `<назва аддона> census` | `census(snapshot)`, `complete(snapshot)`, ваші завдання; іноді `quit` | обчислювати; читати файли; читати пам'ять гри через помічники `ue::` і `mem::Read`, які ніколи не падають; писати в журнал; додавати підказки; передавати результат потоку гри через `thread::Ask(order)` | створювати `Call` чи викликати `Fire`, писати в пам'ять гри (поза помпою обидва відхиляються); ImGui; власні потоки; один запуск довший за 1 с |
| **завантажувач**: `DllMain`, під блокуванням завантажувача Windows | `stop` | ставити власні прапорці; звільняти дані в пам'яті | блокування, очікування, файлові операції, виклики гри, ImGui, нові потоки ([розділ 4](#4-вихід-із-гри-hooksquit-і-hooksstop)) |

Що випливає з таблиці:

- Хуки — це іменовані функції, які підключаються в `src/entry.cpp` рядком `h.<hook> = &Function;`, ніколи не лямбди. `overlay` і `page` визначаються в модулях оверлею, `words` і `tone` — у модулі будь-якого виду, а всі інші хуки — у модулях кадру: у файлах у `src`, крім `src/entry.cpp` і `src/overlay`. Сам `src/entry.cpp` лише підключає хуки. Це перевіряє набір тестів `zsdk-present`.
- Модуль кадру не підключає ImGui і `reshade.hpp` і не викликає функцій, які визначають лише модулі оверлею. Компілятор, перевірка символів об'єктних файлів під час збирання і набір тестів `zsdk-present` ловлять різні способи порушити це правило.
- Поза потоком гри читайте світ через `world::Snapshot()`. `world::Hold()`, викликаний з іншого потоку, пише в журнал `world: the grip was read outside the game thread, this thread gets its own copy from world::Snapshot()` і повертає копію, яка належить цьому потоку і чинна лише до наступного `Hold()` у ньому.
- Хуки GPU і `deviceDestroy` можуть виконуватися раніше за `boot`. SDK спершу відкриває теку даних, тож налаштування і вимкнені ключі вже прочитано, коли такий хук виконується, але нічого з того, що готує `boot`, ще немає.
- На версії гри, до рушія якої ZoneSDK не може прив'язатися, жоден хук помпи від `refresh` до `orderName` не виконується. Хуки кадру, оверлею і D3D та завдання працюють і далі.

## 3. Робота з грою: Ask, step, publish

Виклики гри виконуються лише в помпі. Створення `Call` деінде кидає `zsdk::Refused` («a call was built off the game thread pump»), як і `Fire` («refused off-thread engine call»); жоден код гри не виконується. Тому аддон ділить свою роботу так:

1. **Ask (потік кадру).** `hooks.frame` бачить натискання клавіші і викликає `zsdk::thread::Ask(order)`. Наказ (order) — це ваше власне число `int`. Ask ставить його в чергу і будить потік гри.
2. **Order (потік гри).** SDK викликає `hooks.order(order)` на початку наступного такту, перед `hooks.step`. За такт виконується щонайбільше 2 накази, черга тримає 8 найновіших, а наказ, старший за 2 с або з попереднього світу, відкидається з рядком журналу `request <name> dropped (...)`, де `<name>` дає `hooks.orderName`.
3. **Step (потік гри).** `hooks.step(now)` робить виклики гри і тримає результати у змінних, яких торкається лише потік гри.
4. **Publish (потік гри).** `hooks.publish(now)` копіює те, що потрібно оверлею, у знімок під вашим власним м'ютексом: кожні 250 мс або щотакту, поки `hooks.hot()` повертає true.
5. **Малювання (оверлей).** `hooks.page` і `hooks.overlay` беруть той самий м'ютекс, копіюють знімок і малюють із копії.

Поки `hooks.hot()` повертає true або в черзі чекає наказ, SDK будить потік гри на кожному кадрі, інакше приблизно раз на секунду. `hooks.step` зазвичай виконується щонайбільше раз за кадр гри і лише тоді, коли рушій зв'язано і підключено.

Як це виглядає, за зразком `ZoneHelloHud`:

```cpp
void Frame(const zsdk::Input &input)
{
    if (!input.Focused() || input.Overlaid() || input.Menu()) return;
    if (input.Fires(toggle)) zsdk::thread::Ask(static_cast<int>(Order::Toggle));
}

void OnOrder(int order)
{
    if (order == static_cast<int>(Order::Toggle)) live = !live;
}

void Step(uint64_t)
{
    const zsdk::world::Grip &w = zsdk::world::Hold();
    if (!live || !w.stable || !zsdk::ue::Here(w.body, w.bodyType) || !zsdk::verbs::Ready(kLocation)) return;
    try
    {
        zsdk::Call c(kSpecs, kLocation, w.body);
        zsdk::Fire(c);
        reading = c.Get<zsdk::math::Vec3>("ReturnValue");
    }
    catch (const std::exception &error)
    {
        zsdk::Rare("myhud read", "myhud: reading failed: %s", error.what());
    }
}

void Publish(uint64_t)
{
    std::lock_guard<std::mutex> hold(gate);
    shown = reading;
}

zsdk::math::Vec3 Shown()
{
    std::lock_guard<std::mutex> hold(gate);
    return shown;
}
```

### Без власних потоків: job::Every

Фонова робота виконується як завдання в робочому потоці SDK, ніколи не у власному потоці, таймері чи зворотному виклику пулу потоків. Набір тестів `zsdk-hardrules` не пропускає `CreateThread`, `std::thread`, `std::jthread`, `std::async`, `_beginthread(ex)`, `CreateTimerQueueTimer`, `QueueUserWorkItem`, `TrySubmitThreadpoolCallback`, `SetTimer` і `CreateRemoteThread(Ex)`.

```cpp
void Scan(uint64_t now)
{
    if (zsdk::job::Stopping()) return;
    const int seen = Count(now);
    {
        std::lock_guard<std::mutex> hold(gate);
        found = seen;
    }
    zsdk::thread::Ask(static_cast<int>(Order::Found));
}

void Boot()
{
    zsdk::job::Every("myhud.scan", 500, &Scan);
}
```

- Реєструйте завдання в `hooks.boot` (`h.boot = &Boot;` у `src/entry.cpp`), до запуску робочого потоку SDK. Пізніший виклик відхиляється з рядком журналу. Щонайбільше 8 завдань (`job::kMost`), період від 100 мс, назва від 1 до 32 латинських літер, цифр, `.`, `_` чи `-`.
- Період означає найкоротший проміжок між двома запусками. Завдання запускаються на такті робочого потоку, який триває 100 мс, тож завдання з періодом 100 мс насправді може запускатися лише приблизно раз на 200 мс.
- Завдання виконуються одне за одним і на будь-якій версії гри, навіть коли ZoneSDK не може прив'язатися до рушія. Завдання не робить викликів гри і не пише в пам'ять гри (поза помпою обидва відхиляються). Результат воно передає через власне блокування і `thread::Ask(order)`.
- Довге завдання перевіряє `job::Stopping()`. Воно стає true, коли SDK зупиняється, коли гра просить вийти і під час виходу з процесу.
- Запуск понад 50 мс потрапляє в журнал. Запуск понад 1 с (`job::kStallMs`) вимикає це завдання до кінця сесії. Виняток C++ записується в журнал (щонайбільше раз на хвилину для кожного завдання), а завдання зберігає свій період. Структурований виняток (порушення доступу, переповнення стека) вимикає завдання до кінця сесії і вимикає ключ реєстру `job.<name>` до натискання «Спробувати ще» ([розділ 5](#5-захист-від-збоїв-реєстр-збоїв)).
- Завдання, яке ніколи не повертається, ніщо не зупинить. Через 1 с SDK один раз записує в журнал `job <name> has not returned for <n> ms, the SDK worker waits for it: no other job, census step or exit poll runs until it returns`, тож перевіряйте `job::Stopping()` і повертайтеся.

## 4. Вихід із гри: hooks.quit і hooks.stop

Наприкінці виконуються два хуки, і обіцяють вони різне.

**`hooks.quit`: гра попросила вийти.** На версіях гри, які SDK знає, він стежить за власним прапорцем виходу гри (`GIsRequestingExit`), а також реагує на `WM_QUIT`. Те, що з'явиться першим, запускає одну послідовність виходу: новий такт не починається, `thread::Stopping()` і `job::Stopping()` стають true, кожен наступний `Fire` відхиляється з «engine calls are stopped», потім один раз виконується `hooks.quit`, а в журнал записується `game exit requested (GIsRequestingExit)` або `game exit requested (WM_QUIT)`.

- Він виконується в потоці гри або в робочому потоці SDK, але ніколи одночасно з `hooks.step`.
- Виклики гри вже зупинено: жодних `Fire`, `Call`, `mem::Write`.
- Він може писати ваші власні файли, ненадовго брати ваші власні блокування і казати вашій роботі зупинитися. Довго чекати не варто: гра закривається.
- Завдання або перепис (census), що вже почалися, можуть ще завершуватися в робочому потоці.
- Не покладайтеся на нього. На версії гри, якої ZoneSDK не знає, лишається тільки `WM_QUIT`, а ця гра надсилає його рідко; після збою чи примусового завершення процесу `hooks.quit` не виконується зовсім. Зберігайте важливе під час сесії. Налаштування, змінені через `ini::Apply`, і так зберігаються приблизно за секунду після останньої зміни.

**`hooks.stop`: процес завершується або аддон вивантажується.** Він виконується в `DllMain` під блокуванням завантажувача Windows. Під час виходу з процесу (`shell::Exiting()` повертає true) інших потоків уже немає, і котрийсь із них міг зникнути, тримаючи блокування.

- Жодних блокувань, очікувань, файлових операцій, викликів гри, ImGui і нових потоків.
- Поставте власні прапорці і звільніть дані в пам'яті, не більше.
- `world::Snapshot()` і `census::Current()` там лише пробують взяти свої блокування і дають порожній результат, якщо їх тримав потік, якого вже немає.
- У цей момент SDK пише лише один файл: заздалегідь підготовлену мітку виходу ([розділ 5.3](#53-мітка-виходу)).
- `hooks.stop` виконується всередині огорожі SDK: структурований виняток чи виняток C++ там завершує хук, а вихід триває без рядка в журналі, бо блокування завантажувача не дозволяє його записати.

```cpp
void Stop()
{
    live = false;
}
```

## 5. Захист від збоїв: реєстр збоїв

Хибний виклик гри чи хибна адреса пам'яті можуть призвести до збою гри. Реєстр збоїв (ledger) стежить, щоб та сама помилка не призвела до збою вдруге: наступний запуск знаходить те, що виконувалося, і вимикає саме це.

### 5.1 Мітки збою

- `Fire` позначає виклик гри, коли його ключ уперше виконується на версії гри: перед викликом записує ключ в ini аддона і скидає файл на диск, а після виклику прибирає. Виклик, що повернувся, доводить свій ключ для цієї версії гри і цієї збірки аддона, тож наступні виклики з тим самим ключем нічого не пишуть.
- Якщо гра падає, поки ключ позначено, наступний запуск вимикає цей ключ і тільки його. У журнал записується `safety: <key> pending or watched when the last run ended, disabled`, діагностика показує «Вимкнено після збою: <key>», а наступний виклик із цим ключем відхиляється з «disabled after a crash: <key>».
- Нова версія гри або нова збірка вашого аддона починають докази спочатку, тож перші виклики знову несуть свої мітки.
- Коли мітку неможливо записати (немає теки даних, ini заблоковано), виклик відхиляється з «crash marker unavailable: <key>» (`Policy::strictMarks`, типово увімкнено). Діагностика тоді повідомляє, що мітки збоїв не зберігаються.
- Ключі `engine.wire`, `census.hook`, `job.<name>` і `present.<lane>` належать SDK. Давайте своїм ключам префікс свого аддона, наприклад `myhud.camera`.

### 5.2 Вікна для власного ризикованого коду

Код, що не йде через `Fire`, наприклад сире читання чи запис пам'яті, отримує мітку від `ledger::Window`:

```cpp
zsdk::ledger::Window window("myhud.camera");
if (window.Refused()) return;
float fov = 0.0f;
const bool read = zsdk::mem::Read(zsdk::Addr(camera), kLockedFov, fov);
window.Close();
```

- `Close()` доводить ключ для цієї версії. Вихід з області видимості без `Close()` прибирає мітку без доказу, тож наступне використання знову ставить мітку.
- Вікно відхиляється, коли його ключ вимкнено після збою або його мітку не вдалося записати. Тоді пропустіть цю роботу.
- `mem::Write` потребує відкритого вікна, яке не відхилено, ключа, який не вимкнено, і потоку гри всередині помпи.
- Одночасно відкрито щонайбільше 8 вікон (`Policy::watchKept`, від 1 до 32).

### 5.3 Мітка виходу

Під час звичайного виходу з процесу, коли зникне останнє середовище виконання ефектів ReShade, SDK пише поруч з ini невеликий файл мітки: `<назва ini>.exit`, наприклад `myhud.exit` для `myhud.ini`. Він пише його одним заздалегідь підготовленим записом: без блокування, без виділення пам'яті, без журналу. Після цього ini заморожено, і в цьому процесі його вже ніхто не пише.

Наступний запуск читає мітку:
- мітка відповідає останньому запуску: `safety: the last run <session> ended cleanly (exit mark found)`. Вікна, що лишилися відкритими, закриваються, а не вимикаються; виклик гри, який ще виконувався, вважається збоєм;
- мітки немає: `safety: no clean exit mark from the last run <session>` (цей рядок з'являється, коли лишилася мітка збою або відкрите вікно);
- мітка від іншого запуску або ini змінено після неї: `safety: the exit mark does not match the last run <session>, it counts as a crash`.

В обох випадках запуск вважається збоєм.

Мітка працює на будь-якій версії гри, тож звичайний вихід ніколи не сприймається як збій, навіть якщо `hooks.quit` не виконався.

### 5.4 Спробувати ще

Діагностика перелічує ключі, вимкнені після збою, і показує кнопку «Спробувати ще / Try again» (`ledger::Retry()`). Вона очищає список; наступне використання кожного ключа знову йде з міткою. У журналі з'являється `safety: try again, cleared <keys>`.

Ключі огорожі `present.<lane>` ([розділ 5.5](#55-коли-щось-падає)) очищаються так само. Поки лінія вкладки аддона вимкнена, вкладка показує замість себе власний текст SDK «Частини аддона <name> вимкнено після помилки: <частини>. Подробиці в журналі. / Parts of <name> were switched off after an error: <parts>. The log has the details.», де частини названо мовою гравця, а під ним шлях до журналу, ту саму кнопку і «Скопіювати звіт / Copy report». Лінія знову працює одразу після «Спробувати ще» (`safety: the <lanes> lanes run again after Try again`); після збою в лінії boot чи core в тій самій сесії сам аддон знову запуститься лише з наступним запуском гри.

### 5.5 Коли щось падає

| де | виняток C++ | структурований виняток (порушення доступу, переповнення стека) |
|---|---|---|
| виклик гри (`Call`, `Fire`) | відмова чи хибний параметр кидає вам `zsdk::Refused` або `std::runtime_error`; нічого не вимикається | перехоплюється всередині `Fire`: ключ вимкнено до «Спробувати ще», вам кидається `zsdk::Fault` |
| ваш код у хуку помпи | один рядок журналу (`<stage> error: ...` або `game thread error: ...`); наступний такт виконується як завжди | `structured exception 0x<code> at <module>+0x<offset> in the game thread tick`; з `Policy::haltOnSeh` (типово увімкнено) кожен виклик гри відхиляється до кінця сесії |
| завдання | у журнал, завдання працює далі | завдання вимкнено до кінця сесії, `job.<name>` вимкнено до «Спробувати ще» |
| `hooks.census`, `hooks.complete` | у журнал, хук лишається увімкненим | обидва хуки вимкнено до кінця сесії, `census.hook` вимкнено до «Спробувати ще»; перепис триває |
| `hooks.quit` | у журнал, вихід триває | у журнал, вихід триває |
| `hooks.stop` | хук завершується, у журнал нічого не пишеться, вихід триває | хук завершується, у журнал нічого не пишеться, вихід триває |
| зворотний виклик ReShade (`boot`, `frame`, `overlay`, `page`, `opened`, `deviceDestroy`, хуки GPU, а також власна робота SDK у тих самих подіях) | у журнал записується `<lane> error: ...` щонайбільше раз на хвилину для кожної лінії, наприклад `frame error: ...`; наступного разу виклик виконується знову | огорожа SDK вимикає лінію цього зворотного виклику до кінця сесії, пише один рядок, `structured exception 0x<code> at <module>+0x<offset> in the <lane> lane, ...`, і одразу скидає журнал на диск; ключ реєстру `present.<lane>` (наприклад, `present.frame` чи `present.pipelineBind`) лишається вимкненим і в наступних сесіях, до «Спробувати ще». Лінії frame і toasts вимикаються разом. Збій під час запуску аддона (там виконується `hooks.boot`) або в ядрі SDK вимикає весь аддон до кінця сесії, крім прибирання і збереження наприкінці. Збій у хуку GPU чи пристрою, що прийшов до першого кадру, теж не губиться: ключ вимикається, щойно відкрито теку даних, з рядком журналу `safety: the <lanes> lanes faulted before the data folder opened, they stay disabled`. Перелік ліній є в [API-UA.md](API-UA.md#zsdkhooksh) |

Політика зупинки (halt) визначає, як далеко сягає збій усередині `Fire`:
- `Halt::Key` (типово): вимикається лише ключ, що впав. Усі інші виклики працюють далі.
- `Halt::Session`: ключ, що впав, вимикається, і кожен виклик гри відхиляється до кінця сесії. Фаза показує «Виклики гри зупинено до кінця сесії»; після зупинки помпа лише публікує.

Якщо змінити типові значення `halt` чи `haltOnSeh`, журнал запуску і діагностика покажуть це серед старих правил.

## 6. Версії гри: захисти і самовимкнення

Кожне оновлення гри може зсунути код і дані. Аддон, який читає фіксовану адресу на версії, для якої його не робили, читає сміття. Тому кожен сирий зсув потребує доказу, а можливість аддона, чий доказ не підтвердився, сама вимикається замість того, щоб призвести до збою гри.

- **Спершу рефлексія.** Функцію, яку викликають через `Call`/`Fire`, звіряють із живими даними рефлексії (reflection) гри, щойно рушій готовий. Поле, яке гра описує у своїх даних рефлексії, оголошується як `guard::Field` з рефлексії: перед першим використанням SDK порівнює зсув із `ue::PropertyOffset`. Обидва працюють і після оновлення гри, поки гра й далі їх описує.
- **Поля із захистом.** Поле, якого гра не описує, оголошується як `guard::Field` із доказом `guard::Guard`: коротким маскованим фрагментом машинного коду за певним RVA, який містить цей зсув. Конструктор consteval не скомпілюється, якщо зсуву немає в цих байтах. `Field::Rip` так само доводить адресу. `guard::Set` об'єднує захисти і називає версію гри, з якої вони взяті:
  - `Need::Bytes`: байти кожного захисту збігаються;
  - `Need::ImageSize`: і образ exe має розмір цієї версії;
  - `Need::KnownBuild`: і exe має точний SHA-256 цієї версії.
- **Недоведені поля.** `Field::Unproven` компілюється, але ніколи не стає придатним. Запишіть кожне таке поле з причиною в `tests/unproven-fields.txt` (`zsdk-offsets`).
- **Самовимкнення.** Поле, чий набір вимкнено, відхиляють `guard::Use`, `mem::Read` і `mem::Write`, з одним рядком журналу `guard: field <name> is not usable on this build (...)`. Вмикайте кожну можливість аддона лише тоді, коли `guard::Of(set) == zsdk::guard::State::Ok`; `guard::Ready(set)` каже, що набір уже має вердикт.
- **Без сирих зсувів.** Константа на зразок `kHealthAt = 0x2C8`, буквальний зсув усередині доступу до пам'яті чи арифметика `+ 0x...` не проходять `zsdk-offsets`. `field.Raw()` — помітний обхідний шлях для коду, який сам перевіряє умови; набір тестів рахує кожне використання.

### App::sets: запишіть кожен набір захисту

```cpp
inline constexpr zsdk::guard::Guard kCoreGuards[] = { { .rva = 0x22B5CDE, .bytes = "48 83 EC 28 F3 0F 10 81 CC 02 00 00" } };
inline constexpr zsdk::guard::Set kCoreSet{ "myhud.core", &zsdk::guard::k2bd3f115, kCoreGuards, 1, zsdk::guard::Need::KnownBuild };
constexpr const zsdk::guard::Set *kSets[] = { &kCoreSet };
a.sets = kSets;
```

- SDK перевіряє кожен набір з `App::sets`, щойно рушій готовий, по одному рядку журналу на набір: `guard set myhud.core: 1/1 match, image 0xB954000, on`.
- Набір тестів `zsdk-guards` порівнює з exe гри лише записані набори захисту. Набір захисту, який оголошують ваші вихідні файли, але не записано в `App::sets`, дає попередження, а з `-RequireExe` — помилку.
- Дайте кожному наборові захисту назву-літерал: першим значенням у фігурних дужках, як вище, або як `.name = "..."`. За цим рядком набір тестів знаходить оголошені набори захисту.
- Назви унікальні, а назви `zsdk.*` належать власним наборам SDK.
- `build.cmd -Tests -Exe "<шлях до Stalker2-Win64-Shipping.exe>"` порівнює кожен набір із цим exe, лише читаючи його. На власній версії набору кожен захист мусить збігтися; на будь-якій іншій версії набір тестів виводить прогноз «увімкнено/вимкнено» і не падає. `-LiveExe` знаходить встановлену гру через Steam, а `-RequireExe` робить помилкою відсутній exe або набір, що вийшов вимкненим. Набір, прив'язаний до іншої збірки, ніж exe (по набору на кожну збірку гри, див. [PATCH_DAY-UA.md](PATCH_DAY-UA.md)), показується з поясненням `the set is for build <id> and the exe is build <id>` і не вимагається.

## 7. Об'єкти і стан гри

- **Вказівник на об'єкт — лише припущення.** Гра може знищити будь-який об'єкт будь-коли: підвантаження світу, смерть, зміна рівня. Зберігайте `ue::Mark` від `ue::Seal(thing)` і перевіряйте `ue::Ours(mark)` у потоці гри безпосередньо перед кожним використанням. `ue::Doomed(thing)` повертає true для об'єкта, який знищується, вже є сміттям або недосяжний.
- З `Policy::verifiedOnly` (типово увімкнено) виклик гри відхиляє ціль, яка знищується, і об'єкт, що знищується, переданий параметром.
- **Забувайте старі вказівники, коли змінюється світ.** `hooks.turn` виконується, коли змінюється світ або персонаж гравця; забудьте там кожен вказівник, отриманий до зміни.
- **Тримайте об'єкти через посилання рушія.** Щоб щось жило далі, дайте грі власне посилання на нього: властивість чи компонент об'єкта, який гра тримає. Ніколи не ставте вручну біт кореня чи будь-який інший прапорець у масиві об'єктів рушія. Збирач сміття цієї гри читає власний список коренів, а не біт, а через сирий біт кореня власний виклик гри, що додає об'єкт до коренів, пропускає цей об'єкт. ZoneSDK не має для цього API, а `zsdk-hardrules` забороняє сирі виклики запису (`WriteProcessMemory`, `VirtualProtect`, `_InterlockedOr`).
- **Робіть зміни в грі зворотними в межах сесії.** Те, що ви змінюєте в грі, може потрапити до збереження гравця. Записуйте кожну зміну і скасовуйте її, коли можливість вимикають або змінюється світ. Під час виходу вже нічого не скасуєш: `hooks.quit` виконується після зупинки викликів гри.
- **Не чіпайте небезпечних викликів.** Список `banned=` у `tests/zsdk.cfg` називає виклики, яких аддон робити не має: збереження, вільна камера, проходження крізь стіни, стосунки угруповань, створення чи прибирання аномалій, перемикачі фізики і руху. Стартовий аддон має типовий список; залиште його і доповнюйте.

## 8. Випуск аддона

- **Ніколи не випускайте збірку Debug.** `build.cmd -Config Debug` пише `bin\Debug\<Name>.addon64`, а збірка Release лишається в `bin\<Name>.addon64`. `build.cmd -Verify` відхиляє збірку Debug, а `pack.cmd` пакує лише файл Release і відхиляє файл, позначений як Debug.
- **Перевіряйте перед випуском.** `.\build.cmd -Tests -Verify` збирає аддон, запускає тести (тож `pack.cmd` знає, що файл їх пройшов), запускає аддон у несправжньому хості, перевіряє, що він експортує рівно `NAME` і `DESCRIPTION`, має ресурс версії і не має позначки Debug, а також що у файлі немає шляху збирання, шляху до профілю користувача, шляху з вашим іменем користувача Windows чи іншого абсолютного шляху з літерою диска.
- **Додавайте повідомлення про ліцензії.** `pack.cmd` кладе `NOTICE-ADDON.txt` в архів. Якщо пакуєте вручну, додайте його самі.
- **Не постачайте файлів гри.** Ніколи не кладіть exe гри чи її ресурси у свій аддон або його репозиторій.

## 9. Мова, підказки, теги і клавіші

### Мова

- Аддон говорить лише українською і англійською. Якщо гравець не обрав мову в налаштуваннях аддона, аддон показує українську, коли гра українською, і англійську з будь-якою іншою мовою гри, зокрема з російською. Російської мови як варіанта немає.
- Налаштування пропонують `auto`, `uk` і `en`, а свіжий ini містить `auto`. `lang::Detect()` читає власну мову текстів гри (її файл налаштувань, потім мову гри в Steam, потім мову Windows); збережений код `ru` або будь-який невідомий код стає `auto`.
- Кожен текстовий рядок має і український, і англійський текст, однакові заповнювачі `{n}` в обох, жодних російських літер чи слів і лише знаки, які вміє малювати шрифт SDK. Усе це перевіряє набір тестів `zsdk-texts`.
- SDK постачає типові рядки для діагностики, поля клавіші і фаз (`lang::Defaults()`); ваш рядок з тим самим id має перевагу.

### Підказки

- `App::row.lane` задає висоту, з якої починаються ваші підказки, як частка висоти екрана. Оберіть таку, якої не використовує інший аддон: `new-addon` бере вільну смугу з таблиці ZoneSDK, а `zsdk-identity` попереджає, коли ваша смуга спільна з іншим аддоном.
- Смуга `0` вимикає підказки. Тоді не малюється й власна підказка SDK про непідтримувану версію гри; «Діагностика» все одно її показує.
- Аддон без рядка в таблиці ZoneSDK отримує запасну смугу 0.75 і один рядок у журналі.
- `toast::Push(kind, ...)` приймає види від 0 і більше; види менші за 0 належать SDK.

### Теги

- `Identity::tag` дає назву повідомленню пробудження аддона (`<tag>.GameThread.1`) і його м'ютексу одного екземпляра (`Local\<tag>.Addon.<pid>`). Лише латинські літери і цифри ASCII.
- Тег має бути унікальним серед усіх аддонів, встановлених у гравця. З двох аддонів з одним тегом другий не завантажується: `DllMain` повертає FALSE і надсилає один рядок у вивід налагоджувача (його видно в DebugView), `ZoneSDK: <name> does not load: the tag <tag> is already taken in this process ...`.
- Ставте на початок своє ім'я автора, наприклад `-Tag AuthorMyHud` для `new-addon`. Дайте унікальну назву й `Identity::folder`: це ваша тека в `%LOCALAPPDATA%`.

### Клавіші

- Типово беріть сполучення з Alt, наприклад `ALT+H`: гра призначає звичайні клавіші і рідко сполучення з Alt. Ніколи не призначайте типово клавішу цифрового блока: на багатьох клавіатурах його немає, і `new-addon` такі клавіші відхиляє.
- Дайте гравцеві перепризначити кожну клавішу через `tab::KeyField`. Поле клавіші пише «Цю клавішу також використовує гра» для клавіші, яку гра використовує сама, якщо в сполученні немає ALT; сполучення з CTRL чи SHIFT і такою клавішею цю примітку все одно отримує, тож перевірте його в грі.
- Не реагуйте на клавіші, поки відкрито оверлей ReShade чи меню гри або вікно гри не у фокусі: спершу перевірте `input.Focused()`, `input.Overlaid()` і `input.Menu()`.
- `new-addon` бере клавішу, якої не використовують ні рядки таблиці ZoneSDK, ні зразки, ні аддони поруч із цільовою текою, а `zsdk-identity` попереджає, коли аддон поруч із вашим має ту саму типову клавішу. Інший аддон гравця все одно може її використовувати, тож перевірте її в грі.

## 10. Загальні набори тестів

`build.cmd -Tests` (або `test.cmd`) збирає аддон, а потім запускає ваші власні тести і загальні набори тестів ZoneSDK. Кожен набір виводить один рядок `zsdk-<suite>: N checks, M failures`; перевірка, що не пройшла, виводить над ним `FAIL <message>`, а загальний набір, що не пройшов, додає під ним рядок `zsdk-<suite>: docs\RULES.md (docs\RULES-UA.md in Ukrainian), section 10, zsdk-<suite>, gives the rule behind each message of this suite`. Рядок, що починається з `warning:`, збирання не зупиняє; підсумок рахує такі рядки як попередження тестів.

### zsdk.cfg

`tests\zsdk.cfg` містить по одному `key=value` в рядку. Список пишеться через кому, а шлях — відносно теки аддона, зі скісними рисками (`/`), наприклад `src/poke.cpp`. Ключі, які читають набори:

| ключ | хто читає | що означає |
|---|---|---|
| `name` | zsdk-style | назва аддона; мусить збігатися з назвою, з якою його збирають |
| `comments` | zsdk-style | `forbid` вмикає перевірку відсутності коментарів у `src`, `tests`, файлах `.rc` і `build\make.ps1`; `allow` або відсутній ключ дозволяють коментарі. Стартовий аддон постачається без цього ключа |
| `banned` | zsdk-style | назви викликів, яких не може бути в `src`, ні словом, ні всередині рядка |
| `facade` | zsdk-hardrules | файли, яким можна звертатися до сирого реєстру (`zsdk/test/ledger_raw.h`, `ledger::raw`), лише всередині блоків `#if defined(ZSDK_TESTS)` |
| `memory` | zsdk-hardrules | файли, яким можна писати в пам'ять гри через `mem::Poke`, без вікна збою |
| `identity.same` | zsdk-identity | назви тек інших аддонів, яким можна мати ваш тег, наприклад старої копії вашого ж аддона |
| `workspace` | zsdk-identity | тека, яку переглядає пошук збігів тегів, відносно теки аддона |
| `define` | zsdk-identity | префікс макросів аддона; мусить збігатися з тим, з яким його збирають. Його пише `new-addon` |
| `registry` | zsdk-identity | id аддона в таблиці ZoneSDK; мусить збігатися з `Identity::registry`. Його пише `new-addon` |
| `present.allow` | zsdk-present | назви функцій, які модулі кадру можуть викликати, хоча функцію з такою назвою визначають лише модулі оверлею |

Змінні середовища: `ZSDK_WORKSPACE` має перевагу над `workspace=`. `ZSDK_EXE` і `ZSDK_REQUIRE_EXE=1` керують `zsdk-guards`; `build.cmd -Exe`, `-LiveExe` і `-RequireExe` ставлять їх за вас.

### zsdk-present

Модулі кадру вільні від ImGui і коду оверлею; хуки — це іменовані функції в модулях правильного виду. Правила: [розділ 2](#2-потоки-що-де-може-виконуватися).

| повідомлення після FAIL | що робити |
|---|---|
| `the add-on tree has present units and src/entry.cpp` | залиште `src/entry.cpp` і хоча б один модуль кадру |
| `no <word> in the present unit <file>` | перенесіть код з ImGui, `reshade.hpp`, `zsdk/overlay.h`, `zsdk/paint.h`, `paint::`, `tab::`, `overlay::` чи `IM_COL32` до `src/overlay` |
| `the present unit <file> calls the overlay-only function <name>` | викликайте її з модуля оверлею; якщо це інша функція з тією самою назвою, додайте назву до `present.allow` |
| `the build wrote the object symbol table: <path>`, `the present objects reference external symbols`, `the overlay objects define symbols that no present object defines` | перевірці символів нічого перевіряти; збирайте власним `build.cmd` аддона, який пише цю таблицю |
| `a present object uses a symbol defined only in overlay objects: <object> <symbol>`, `no present object references an overlay-only symbol (...)` | модуль кадру звертається до коду оверлею, можливо, через написане вручну оголошення; перенесіть виклик до модуля оверлею |
| `entry.cpp registers through zsdk::shell::Main`, `no <word> in entry.cpp` | `src/entry.cpp` лише підключає хуки і передає `DllMain` до `zsdk::shell::Main`; ImGui там немає |
| `the hook <hook> is wired to a lambda; hooks are named functions`, `the hook <hook> is wired to a named function: <target>` | пишіть `h.<hook> = &Function;` |
| `the hook <hook> is a known ZoneSDK hook` | такого поля в `zsdk::Hooks` немає |
| `the hook <hook> is an overlay function defined in src/overlay: <name>`, з `, which is defined in src/entry.cpp`, `, which a present unit defines too` або `, which no overlay unit defines` | визначте `overlay` і `page` у `src/overlay`, по одному разу |
| `the hook <hook> is a function of a present unit (present units are src/*.cpp and their subfolders, except src/entry.cpp and src/overlay): <name>` з місцем, де знайдено `<name>` | визначте хук у модулі кадру: не в `src/entry.cpp`, який лише підключає хуки, і не в `src/overlay`; дві функції з однією назвою в модулі кадру і в модулі оверлею потребують різних назв |
| `the toast hook <hook> is one add-on function: <name>` | визначте `words` і `tone` по одному разу, в одному модулі |
| `entry.cpp wires the present hooks, <n>`, `entry.cpp wires the tab page` | підключіть щонайменше два хуки кадру і `page` |
| `the overlay-only call set is not empty, <n>` | випуск ZoneSDK пошкоджено; повідомте про це |

### zsdk-hardrules

Жодних звертань до коду гри в обхід SDK, власних потоків і сирих записів, охайна точка входу і збирання із закріпленим випуском. Правила: розділи [3](#3-робота-з-грою-ask-step-publish), [5](#5-захист-від-збоїв-реєстр-збоїв) і [7](#7-обєкти-і-стан-гри).

| повідомлення після FAIL | що робити |
|---|---|
| `no <word> in <file>` для `Ride(`, `ProcessEvent`, `__try`, `__except`, `native_bindings::`, `detail::engine`, `detail/`, `zsdk::detail` | викликайте функції гри лише через `Call`/`Fire`; нутрощі SDK і огорожі SEH не для коду аддона |
| `no <word> in <file>` для `SetWindowsHookEx`, `VirtualProtect`, `WriteProcessMemory`, `_InterlockedOr` | жодних власних хуків чи сирих записів; пишіть у пам'ять гри через `mem::Write` всередині вікна збою |
| `no <word> in <file>: background work runs through zsdk::job::Every on the SDK worker, ...` для `CreateThread`, `std::thread` і викликів таймерів та пулу потоків | використовуйте `job::Every` ([розділ 3](#без-власних-потоків-jobevery)) |
| `only the listed test facade reaches the raw ledger: <file>`, `the facade reaches the raw ledger only inside #if defined(ZSDK_TESTS) blocks: <file>` | сирий реєстр лише для тестів; запишіть файл у `facade=` і тримайте звертання всередині `#if defined(ZSDK_TESTS)` |
| `raw game memory writes outside a crash window only in a listed memory facade: <file>` | пишіть через `mem::Write` з `ledger::Window` або запишіть файл у `memory=` |
| `exports come only from ZSDK_ADDON: <file>` | жодного власного `dllexport` |
| `one ZSDK_ADDON and one DllMain`, `DllMain only hands over to zsdk::shell::Main` | залиште `src/entry.cpp` таким, як у стартовому аддоні |
| `zsdk.lock pins this ZoneSDK version`, `zsdk.lock pins the manifest of the release it builds against` | `build\zsdk.lock` називає інший випуск, ніж той, що знайшло збирання; виправте `version=` і `manifest=` ([VERSIONING-UA.md](VERSIONING-UA.md)) |
| `the add-on builds against a release snapshot, not the working tree: <path>` | збирайте з текою `release\<версія>` з пакета |
| `tests drive no native code: <file>` | жодних `__try` і `ProcessEvent` у `tests` |

Доки випуск ZoneSDK не містить `zsdk/job.h`, слова таймерів і пулу потоків дають лише попередження (`hardrules: <word> in <file>: ...`). ZoneSDK 1.0 його містить, тож вони зупиняють збирання.

### zsdk-style

Налаштування аддона, коментарі, літерали і `build\make.ps1`. Правила: [розділ 10](#zsdkcfg) і [розділ 7](#7-обєкти-і-стан-гри).

| повідомлення після FAIL | що робити |
|---|---|
| `tests/zsdk.cfg exists`, `zsdk.cfg names the add-on that is built` | тримайте `tests\zsdk.cfg` з `name=<назва аддона>` |
| `zsdk.cfg comments= is forbid or allow: <value>` | напишіть одне з цих двох слів |
| `no comments in <file> (line <n>)`, `no comments in make.ps1 line <n>` | лише з `comments=forbid`: приберіть коментар |
| `every literal is closed in <file>` | рядок чи символьний літерал не закрито |
| `build/make.ps1 exists`, `make.ps1 builds through the pinned ZoneSDK module` | залиште `build\make.ps1` зі стартового аддона |
| `make.ps1 is pure ASCII, line <n>`, `make.ps1 has no absolute drive path` | жодних інших літер і шляхів з літерою диска в `build\make.ps1` |
| `build/make.ps1 deploys nothing: no <word>` | збирання ніколи не копіює файли в теку гри; встановлення робить гравець |
| `forbidden call <name> is absent from <file>` | цей виклик є у списку `banned=` ([розділ 7](#7-обєкти-і-стан-гри)) |

Лише попередження: `style: a raw tick difference '<text>' in <file> line <n>, ...`. Пишіть `zsdk::Age(now, at)`, що дає 0, коли позначка часу пізніша за now, замість `now - at`.

### zsdk-texts

Правило мови. Правила: [розділ 9](#мова).

| повідомлення після FAIL | що робити |
|---|---|
| `the add-on has language rows, <n>`, `row ids are unique: <id>` | дайте кожному текстові власний id |
| `both languages have text: <id>` | заповніть український і англійський текст |
| `no Russian letters: <id>` | у тексті є російські літери чи слова; пишіть українською |
| `uk and en use the same {n} slots: <id>` | обидві мови мають ті самі заповнювачі `{0}`, `{1}` ... |
| `the paint font draws every sign of <id> <U+...>` | замініть перелічені знаки |
| `no Russian language is offered in <file>: "<literal>"` | приберіть код російської мови (`ru`, `rus`, `russian`, `ru-ru`, `ru_ru` чи id, що закінчується на `.ru`, `.rus`, `.russian`) |
| `a fresh ini gives the language auto (the game language: uk gives UA, every other culture EN), the add-on default is <code>` | зробіть `auto` типовим значенням свого налаштування мови |
| `a fresh data folder opens` | схема налаштувань не відкриває свіжий ini; перевірте `Schema()` |

`SKIPPED zsdk-texts: the add-on has no settings schema ...` з'являється лише разом із провалом `zsdk-identity`: ZoneSDK 1.0 потребує схеми налаштувань.

### zsdk-identity

Унікальні назви. Правила: [розділ 9](#теги).

| повідомлення після FAIL | що робити |
|---|---|
| `the identity has a name, a tag and a version`, `the identity name is the built add-on` | заповніть `App::identity`; його назва — це назва аддона |
| `the App has a settings schema (App::schema); without one ZoneSDK opens no data folder, settings or log for the add-on and leaves it off` | задайте в `App::schema` схему `ini::Schema` (у стартовому аддоні вона є в `src/settings.cpp`) |
| `zsdk.cfg registry= names the registry id of the identity: <cfg> against <id>`, `zsdk.cfg define= is the define the build uses: <cfg> against <define>` | узгодьте `registry=` і `define=` у `tests\zsdk.cfg` з `Identity::registry` і префіксом, з яким збирають аддон, або приберіть ці рядки |
| `the tag is plain ASCII letters and digits` | змініть тег |
| `the add-on has a registry row, its own or the ZoneSDK one: <id>`, `the registry row carries the same tag`, `the registry row has the identity registry id` | задайте `App::row` з тими самими id і тегом, що в `App::identity` |
| `the ZoneSDK table agrees with the add-on row for <id>`, `no other registry row uses the tag <tag>: <id>` | id чи тег уже зайнято в таблиці ZoneSDK; оберіть інший |
| `another tree uses the tag <tag> for its wake or mutex name: <path>` | інша тека аддона поруч із вашою має ваш тег; змініть тег або, якщо це ваша власна копія, запишіть ту теку в `identity.same` |
| `the workspace for the collision scan exists: <path>` | `workspace=` або `ZSDK_WORKSPACE` вказує на теку, якої немає |
| `registry tags are unique: <tag>`, `the wake message derives from the tag`, `the mutex derives from the tag` | випуск ZoneSDK пошкоджено; повідомте про це |

Лише попередження:
- `identity: <id> is not in the ZoneSDK registry table, its own row is used`: звичайна справа для кожного аддона, якого немає в таблиці ZoneSDK.
- `identity: toast lane <lane> is shared with <id>`: оберіть іншу смугу.
- `identity: toast lane <lane> is also used by the add-on in <folder>; its toasts and yours would overlap` і `identity: the key <key> is also a default key of the add-on in <folder>`: аддон поруч із вашим має ту саму смугу чи типову клавішу; оберіть іншу.
- `identity: the collision scan stopped after 5000 folders ...`: вкажіть у `workspace=` або `ZSDK_WORKSPACE` теку, де лежать ваші аддони.

Типово пошук переглядає теки поруч із вашим аддоном, у яких є `build\zsdk.lock`.

| повідомлення після FAIL | що робити |
|---|---|
| `a raw layout constant outside zsdk::guard::Field: <name> in <file>` | зробіть зсув полем `guard::Field` з доказом через захист, RIP чи рефлексію |
| `a literal offset inside a memory access: <text> in <file>` | читайте і пишіть через `guard::Field` |
| `hex literal arithmetic, an offset belongs in a Field: <text> in <file>` | жодних `+ 0x...` на адресах; використовуйте `guard::Field` |
| `the unproven field <name> is listed with a reason in tests/unproven-fields.txt` | додайте `<name>: <причина>` до `tests\unproven-fields.txt` |

### zsdk-specs

Ваша таблиця дієслів у звірці з дампом функцій гри. Правила: [розділ 3](#3-робота-з-грою-ask-step-publish).

| повідомлення після FAIL | що робити |
|---|---|
| `the add-on has a verb table` | `App::specs` порожня |
| `WorldVerbs gives <Owner.Name> the index of that verb in App::specs, or -1 for none (...)` | `WorldVerbs{}` означає індекси каталогу `verbs::common::kWorld`. Почніть свою таблицю з нього (`verbs::Join(common::kWorld, kOwn)`) або задайте кожну роль `WorldVerbs` самі: `-1`, якщо ролі немає. ZoneSDK 0.1.x читав `WorldVerbs{}` як «жодних дієслів світу», тож аддон, перенесений з 0.1.x, задає ролі сам |
| `the dump of <build> agrees with <Owner.Name> (<why>)` | параметри, зсуви, розміри чи розмір блоку функції відрізняються від вашого `Spec`; виправте `Spec` |
| `the function dump of <build> is readable, <n> rows` | файл випуску `data\builds\<build>\ufunctions.txt` пошкоджено; повідомте про це |

`SKIPPED zsdk-specs: the ZoneSDK release has no function dump ...` означає, що у випуску немає `ufunctions.txt`; тоді дієслова перевіряються лише в грі. Дієслово, якого немає в дампі, лише рахується. SDK звіряє кожне дієслово з живими даними рефлексії гри, щойно рушій готовий, а роль, що називає інше дієслово, вимикається на першому кроці світу з одним рядком журналу.

### zsdk-guards

Набори захисту і справжній exe гри. Правила: [розділ 6](#6-версії-гри-захисти-і-самовимкнення).

| повідомлення після FAIL | що робити |
|---|---|
| `an add-on guard set does not take the zsdk.* names of the SDK's own sets` | перейменуйте набір |
| `every guard set has a name`, `guard set names are unique: <name>` | дайте кожному наборові власну назву |
| `the guard set <name> points at its guards` | набір має кількість, але не має захистів |
| `the guard set <name> names the build its image size comes from` | набір з `Need::ImageSize` чи `Need::KnownBuild` називає свій `guard::Build` |
| `the guard bytes parse: <name> <rva>` | пишіть байти парами шістнадцяткових цифр через пробіл, `??` для замаскованого байта |
| `the guard lies inside the image of <build>: <name> <rva>` | RVA разом із байтами виходить за межі образу |
| `the exe is build <id> of the set <name> by SHA-256, so every guard and the image size match, ...` | на власній версії набору захист не збігся: байти чи RVA хибні |
| `the guard set <name> (...) is not listed in App.sets ...; under -RequireExe every declared set is listed in .sets` | запишіть набір в `App::sets` |
| `the guard set <id> in <file> has no literal name, ...; under -RequireExe ...` | напишіть назву рядковим літералом: першим значенням у фігурних дужках або як `.name = "..."` |
| `an exe is given for the guard check under -RequireExe (...)`, `the exe <file> opens read-only as a PE image under -RequireExe (...)` | передайте `-Exe` з exe, який можна прочитати, або `-LiveExe` |
| `the set <name> comes out on under -RequireExe, ...` | з `-RequireExe` кожен набір мусить бути увімкненим для цього exe, крім набору, прив'язаного до іншої збірки |
| `the SDK's own guard sets are named zsdk.*` | випуск ZoneSDK пошкоджено; повідомте про це |

Без exe набір тестів виводить `SKIPPED zsdk-guards: no exe given (ZSDK_EXE, make -Exe or -LiveExe), ...` і не відкриває жодного файлу; exe, який не вдається прочитати, дає `SKIPPED zsdk-guards: the exe <file> cannot be used (...)`. Він ніколи не копіює exe.
